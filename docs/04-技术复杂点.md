# 04-技术复杂点

## 1. 模块边界控制

Synapse Framework 最大的复杂点不是单个技术实现，而是防止基础模块被业务语义污染。

必须持续检查：

- 是否出现业务名词。
- 是否出现业务 Controller。
- 是否出现业务 Entity / Mapper / migration。
- 是否出现业务权限码。
- 是否出现平台服务职责。
- 是否出现不合理模块依赖。

任何新增能力都应先判断属于 Framework、Platform Service 还是 Business Application。

## 2. OperationContext 传播

`OperationContext` 要覆盖多种执行入口：

- HTTP。
- MQ。
- Job。
- Async。
- 内部服务调用。

复杂点：

- 上下文必须可快照和恢复。
- 异步场景不能默认丢失操作者。
- 不能把当前用户绑定死在 `security` 或 `web`。
- data、audit、mq 必须通过 core 契约获取上下文。

## 3. Web 异常链路

Servlet MVC 存在两个异常阶段：

```text
Filter 阶段
MVC Controller 阶段
```

复杂点：

- Filter 阶段异常不会自动进入 `@RestControllerAdvice`。
- 普通 Framework Filter 异常由 `SynapseExceptionBridgeFilter` 桥接。
- Resource Server 的认证与授权失败由专用 401/403 handler 处理。
- MVC 阶段由 `GlobalExceptionHandler` 统一处理。
- 常见请求错误不能落到 500。
- `synapse-webmvc` 不得依赖 `synapse-security` 或内置 OAuth2 Resource Server。

## 4. Security 与 OAuth2 边界

`synapse-security` 只做 Web 无关安全主体、上下文、权限检查和密码编码；认证协议由 OAuth2 Resource Server 适配模块承担。

复杂点：

- Gateway 可以验证 Token，但下游服务必须独立验证签名、issuer、audience、有效期和 token contract。
- Gateway 与下游之间只传播 Bearer Token。
- 用户、角色、权限等身份 Header 不可信，不能作为认证依据。
- JWT claims 映射出的主体要同时进入 Synapse `CurrentPrincipalContext` 与 `OperationContext`。
- Servlet 请求结束后必须关闭 PrincipalContextScope。
- Reactive 场景必须使用 Reactor Context，不能依赖 Servlet ThreadLocal。
- `PermissionChecker` 必须支持显式调用，不能只依赖 AOP。
- `@RequirePermission` 只是声明式适配。
- security 错误码留在 `synapse-security`，core 只保留通用错误码。

## 5. Data 自动填充

复杂点：

- data 不能依赖 security。
- 创建人、更新人等信息来自 `OperationContextProvider`。
- 没有上下文的任务、MQ、异步场景必须由调用方显式建立上下文。
- 不能简单默认 system，否则会损失追溯能力。

## 6. Cache 并发能力

复杂点：

- Redis Lua 原子性。
- 可重入锁释放安全。
- 幂等 key 的生命周期。
- 限流窗口精度。
- L1 / L2 缓存一致性。
- 测试不能写业务 key。

## 7. MQ 契约收敛

复杂点：

- `synapse-messaging` 不直接绑定 MQ SDK。
- `synapse-messaging` 不直接落库。
- 发布和消费只定义 SPI、模板、错误码、异常分类和幂等契约，不实现具体 Broker 适配。
- 发布端读取上下文必须通过 `OperationContextProvider`，避免直接绑定 ThreadLocal 读取方式。
- MQ 异常只能表达 Framework 技术失败，不能承载业务错误码或原生 Broker SDK 异常。
- MQ Header 不传播 Bearer Token、roles 或 permissions。
- 不实现钉钉、企业微信、短信、邮件等通知渠道。
- 不实现 Redis 幂等、数据库消息表、Outbox 或事务消息。
- 不做消息中心后台。

## 8. File 能力收敛

复杂点：

- file 只做存储抽象，不做文件中心。
- 本地实现要防路径穿越。
- 上传下载 API、附件表、文件权限、预览、转码都不进入 Framework。

## 9. 自动配置边界

所有自动配置必须满足：

- 不强制覆盖用户 Bean。
- 能按条件装配。
- 外部连接型能力不得在默认情况下造成测试或启动失败。
- Filter、AOP、Adapter 必须有明确启用条件和顺序。
- 通用 Web 自动配置不得隐式启用 OAuth2 Resource Server。

## 10. 注释要求

公共 API、SPI、Port、Annotation、AutoConfiguration、Properties、并发控制、上下文传播、异常桥接等必须有必要注释。

注释只解释原因、边界和风险，不重复代码本身。
