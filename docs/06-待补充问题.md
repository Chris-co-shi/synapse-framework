# 06-待补充问题

本文档记录一阶段已关闭问题、二阶段已确认事项，以及仍需后续任务讨论的问题。

## 1. 一阶段已关闭的问题

以下问题在一阶段已经形成结论：

- `synapse-web` 一阶段只保留 Servlet MVC，不再混入 WebFlux。
- Gateway / WebFlux 后续单独建模块，不放入当前 `synapse-web`。
- `synapse-security` 不引入 Spring Security Web / SecurityFilterChain / MethodSecurity。
- trusted-header、PermissionChecker、`@RequirePermission` 已作为一阶段安全基础闭环。
- `SynapseAuthenticationException`、`SynapseAccessDeniedException` 已下沉到 core。
- security 场景细分错误码保留在 `synapse-security`。
- message 只做契约，不做 MQ SDK、渠道 SDK、DB Repository。
- file 一阶段只做存储抽象和本地轻量实现，不做文件中心。
- cache 一阶段只做缓存、锁、限流、幂等基础设施。

## 2. 二阶段已确认事项

以下事项已经确认，后续不再反复讨论，除非项目阶段发生重大变化。

### 2.1 Framework 总边界

- Synapse-Framework 下所有 module 都是技术支持框架。
- Framework module 不能启动。
- Framework module 不能包含业务代码。
- Framework 最多提供技术约束、抽象、模型、SPI / Port、默认轻量实现、自动装配、上下文传播、工具能力和 starter 组合能力。
- 可启动服务统一属于 Synapse-Platform。

### 2.2 synapse-mq

- `synapse-message` 已改为 `synapse-mq`。
- `synapse-mq` 只做 MQ 技术抽象。
- `synapse-mq` 不做 message-service。
- 站内信、短信、邮件、消息模板、消息中心后台属于 Platform。

### 2.3 synapse-config

- `synapse-config` 可以在二阶段作为 Framework 技术模块规划。
- Framework 中的 `synapse-config` 只能做配置抽象、配置客户端、运行时配置读取、解析、缓存、刷新扩展点。
- Framework 中的 `synapse-config` 不做 config-service。
- 配置管理、配置发布、配置审批、配置数据库表、配置中心后台属于 Platform。

### 2.4 WebMVC / WebFlux

- 当前 `synapse-web` 偏 Servlet MVC。
- Gateway 是 WebFlux / Spring Cloud Gateway 技术栈，不能引用偏 WebMVC 的 `synapse-web`。
- WebMVC / WebFlux 拆分进入 TASK-202。
- `synapse-webflux` 只能做 WebFlux 技术支撑，不能做 gateway 服务。
- 可启动 gateway 属于 Synapse-Platform。

### 2.5 synapse-time

- 时区设计进入二阶段。
- 二阶段按独立 `synapse-time` 模块规划，不并入 `synapse-core`。
- `synapse-time` 只做时间、时区、UTC 查询边界、序列化等技术能力。
- 组织、工厂、用户资料、时区配置后台属于 Platform 或业务应用。

### 2.6 synapse-oauth2

- 二阶段 `synapse-oauth2` 只允许 JWT / JWK / Token 解析 / Token denylist / Resource Server 辅助能力。
- 二阶段 Framework 不做 Authorization Server 实现。
- 登录、客户端管理、用户认证、授权码流程、授权记录管理、IAM 后台属于 Platform `synapse-iam`。

### 2.7 暂存目录

- `synapse-task`、`synapse-tenant`、`synapse-data-permission` 若目录存在但未进入 root reactor，只能视为非正式 reactor module / 暂存目录 / 历史残留。
- 后续是否纳入二阶段，需要单独 TASK 评估。
- 不得在无任务约束的情况下把这些目录加入 reactor。

## 3. 二阶段候选问题

以下问题留给二阶段具体 TASK 或后续平台服务讨论。

### 3.1 Gateway / WebFlux

- TASK-202 如何处理 `synapse-web` 到 `synapse-webmvc` 的迁移兼容性。
- `synapse-webflux` 的 Result 契约是否复用 MVC 的 Result，还是抽取更基础的 response model。
- WebFlux 异常响应如何与 MVC 保持一致。
- WebFlux 下 OperationContext 如何与 Reactor Context 协同。

### 3.2 Tenant / Data Permission

- 是否恢复 `synapse-tenant` 进入 reactor。
- 是否恢复 `synapse-data-permission` 进入 reactor。
- 租户上下文是否复用 `OperationContext`。
- DataScope / ABAC 是否由独立模块实现。
- 多表 join 场景的数据权限字段冲突如何处理。

### 3.3 Task / Async

- 是否新增 framework 侧任务技术抽象模块，还是仅在 core / cloud / mq 中提供上下文传播能力。
- 定时任务、异步任务、MQ 消费场景如何统一建立 `OperationContext`。
- 默认 system actor 是否允许，还是必须显式指定 actor。
- 任务失败后的审计和追踪如何记录。

### 3.4 MQ Runtime Adapter

`synapse-mq` 已确认只做 MQ 技术抽象。后续仍需讨论：

- 是否提供 RocketMQ / Kafka / RabbitMQ adapter。
- adapter 是否作为独立子模块或 optional dependency。
- 是否提供 outbox / reliable message 运行时抽象。
- 是否提供死信、补偿、重试的默认轻量实现。

### 3.5 File Adapter

`synapse-file` 已确认只做文件存储抽象。后续仍需讨论：

- 是否支持 MinIO / OSS / S3 adapter。
- adapter 是否作为独立子模块或 optional dependency。
- 本地轻量实现是否仅用于开发和测试。

### 3.6 Cloud / Remote Call

- 是否新增 `synapse-cloud`。
- OpenFeign / LoadBalancer / Resilience4j 是否作为独立 adapter。
- 远程调用上下文传播是否复用 `OperationContextSnapshot`。
- 服务间鉴权是否与 trusted-header 统一。

## 4. 版本与发布问题

- Spring Boot 3.5.x 后续补丁版本跟进策略。
- Spring Cloud / Spring Cloud Alibaba 是否进入二阶段 BOM。
- Seata / RocketMQ / Nacos 是否作为 Platform 层依赖，而不是 Framework 一阶段依赖。
- GitHub Packages / Maven Central 发布策略。
- 是否区分 internal BOM 与 public BOM。

## 5. 工程治理问题

- 是否补充模块级 Skill 文档。
- 是否补充自动生成 API 文档。
- 是否引入依赖边界检查脚本。
- 是否将 `mvn clean test`、`mvn validate`、边界搜索固化为 CI。
- 历史保留目录是否在二阶段前归档或删除。

## 6. 不应再反复讨论的问题

除非项目阶段变化，以下结论保持冻结：

- 一阶段不做业务 Controller。
- 一阶段不做业务 Entity / Mapper / migration。
- 一阶段不做 starter。
- 一阶段不做 Gateway / WebFlux。
- 二阶段 WebMVC / WebFlux 拆分进入 TASK-202。
- 二阶段时区设计由 `synapse-time` 独立模块规划。
- Framework 不做平台文件中心、消息中心、配置中心、审计中心、任务中心。
- Framework 不做 IAM。
- Framework 不做 ABAC / DataScope 业务实现。
- Framework 不做多租户平台实现。
