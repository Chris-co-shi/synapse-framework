# 06-待补充问题

本文档记录一阶段已关闭问题、二阶段已确认事项，以及仍需后续任务讨论的问题。

## 1. 一阶段已关闭的问题

以下问题在一阶段已经形成结论：

- `synapse-web` 一阶段只保留 Servlet MVC，不混入 WebFlux。
- TASK-202 已将 `synapse-web` 拆分为 `synapse-webmvc` 和 `synapse-webflux`，不保留兼容层。
- `synapse-security` 不引入 Spring Security Web / SecurityFilterChain / MethodSecurity。
- `SecurityContext`、PermissionChecker、`@RequirePermission` 已形成 Web 无关安全基础闭环。
- `SynapseAuthenticationException`、`SynapseAccessDeniedException` 已下沉到 core。
- security 场景细分错误码保留在 `synapse-security`。
- message 只做契约，不做 MQ SDK、渠道 SDK、DB Repository。
- file 一阶段只做存储抽象和本地轻量实现，不做文件中心。
- cache 一阶段只做缓存、锁、限流、幂等基础设施。

二阶段已明确撤销一阶段的 trusted-header 身份恢复方案，不再保留相关模块、协议和配置。

## 2. 二阶段已确认事项

以下事项已经确认，后续不再反复讨论，除非项目阶段发生重大变化。

### 2.1 Framework 总边界

- Synapse-Framework 下所有 module 都是技术支持框架。
- Framework module 不能启动。
- Framework module 不能包含业务代码。
- Framework 最多提供技术约束、抽象、模型、SPI / Port、默认轻量实现、自动装配、上下文传播、工具能力、测试、文档和 Skill。
- Framework 不提供 starter 聚合包。
- Framework 不提供 demo / example / sample application。
- 可启动服务统一属于 Synapse-Platform。

### 2.2 synapse-mq

- `synapse-message` 已改为 `synapse-mq`。
- `synapse-mq` 只做 MQ 技术抽象。
- `synapse-mq` 不做 message-service。
- 站内信、短信、邮件、消息模板、消息中心后台属于 Platform。

### 2.3 synapse-config

- Framework 中的 `synapse-config` 只做配置抽象、配置客户端、运行时配置读取、解析、缓存和刷新扩展点。
- Framework 中的 `synapse-config` 不做 config-service。
- 配置管理、配置发布、配置审批、配置数据库表、配置中心后台属于 Platform。

### 2.4 WebMVC / WebFlux

- `synapse-webmvc` 承接 Servlet MVC 通用技术支撑。
- `synapse-webflux` 提供 WebFlux 通用技术支撑。
- Gateway 是 WebFlux / Spring Cloud Gateway 技术栈，不能引用 `synapse-webmvc`。
- `synapse-webflux` 不能做 gateway 服务。
- 可启动 gateway 属于 Synapse-Platform。
- OAuth2 Resource Server 不并入通用 Web 模块，继续由独立的 WebMVC / WebFlux Resource Server 模块承担。

### 2.5 synapse-time

- 时间和时区能力由独立 `synapse-time` 模块承载，不并入 `synapse-core`。
- `synapse-time` 只做时间、时区、UTC 查询边界、序列化等技术能力。
- 组织、工厂、用户资料、时区配置后台属于 Platform 或业务应用。

### 2.6 Security / OAuth2

- `synapse-security` 只提供 Web 无关安全主体、SecurityContext、PermissionChecker、权限注解和密码编码。
- `synapse-security-webmvc` 与 trusted-header 身份协议已移除。
- Gateway 与下游之间只传播 Bearer Token，不传播可直接信任的用户、角色或权限 Header。
- Gateway 可以验证 Token，但下游服务必须独立验证签名、issuer、audience、有效期和 token contract。
- OAuth2 已拆分为 `synapse-oauth2-core`、`synapse-oauth2-authorization-server-support`、`synapse-oauth2-resource-server-webmvc`、`synapse-oauth2-resource-server-webflux`。
- Framework 不做完整 Authorization Server 业务实现。
- 登录、客户端管理、用户认证、授权码流程、授权记录管理、IAM 后台属于 Platform `synapse-iam`。

### 2.7 暂存目录

- `synapse-task`、`synapse-tenant`、`synapse-data-permission` 若目录存在但未进入 root reactor，只能视为非正式 reactor module / 暂存目录 / 历史残留。
- 后续是否纳入，需要单独 TASK 评估。
- 不得在无任务约束的情况下把这些目录加入 reactor。

### 2.8 Starter / Demo

- 本项目不创建 `synapse-starter-*`。
- 本项目不创建 starter 聚合包。
- 本项目不创建 demo / example / sample application。
- 本项目不创建任何可启动示例工程。
- 业务系统按需直接引用具体 module。

## 3. 二阶段候选问题

以下问题留给具体 TASK 或后续平台服务讨论。

### 3.1 Gateway / WebFlux

- WebFlux 异常响应如何持续与 MVC 保持一致。
- WebFlux 下 OperationContext 如何与 Reactor Context 协同。
- Gateway 路由、入口限流和入口级鉴权策略属于 Platform 实现。

### 3.2 Tenant / Data Permission

- 是否恢复 `synapse-tenant` 进入 reactor。
- 是否恢复 `synapse-data-permission` 进入 reactor。
- 租户上下文是否复用 `OperationContext`。
- DataScope / ABAC 是否由独立模块实现。
- 多表 join 场景的数据权限字段冲突如何处理。

### 3.3 Task / Async

- 是否新增 Framework 侧任务技术抽象模块，还是仅在 core / cloud / mq 中提供上下文传播能力。
- 定时任务、异步任务、MQ 消费场景如何统一建立 `OperationContext`。
- 默认 system actor 是否允许，还是必须显式指定 actor。
- 任务失败后的审计和追踪如何记录。

### 3.4 MQ Runtime Adapter

`synapse-mq` 已确认只做 MQ 技术抽象。后续仍需讨论：

- 是否提供 RocketMQ / Kafka / RabbitMQ adapter。
- adapter 是否作为独立子模块或 optional dependency。
- 是否提供 outbox / reliable message 运行时抽象。
- 是否提供死信、补偿、重试的默认轻量实现。

### 3.5 File Adapter

`synapse-file` 已确认只做文件存储抽象。后续仍需讨论：

- 是否支持 MinIO / OSS / S3 adapter。
- adapter 是否作为独立子模块或 optional dependency。
- 本地轻量实现是否仅用于开发和测试。

### 3.6 Cloud / Remote Call

- `synapse-cloud` 已进入 reactor。
- OpenFeign 已作为服务间调用技术适配实现。
- LoadBalancer / Resilience4j 后续如需支持，应保持技术扩展点边界。
- 远程调用上下文传播继续复用 `OperationContextSnapshot`。
- 服务间 Bearer Token 转发应复用 OAuth2 Core 的 `BearerTokenProvider`，不得把 Token claims 拆成身份 Header。

## 4. 版本与发布问题

- Spring Boot 3.5.x 后续补丁版本跟进策略。
- Spring Cloud / Spring Cloud Alibaba 版本跟进策略。
- Seata / RocketMQ / Nacos 是否作为 Platform 层依赖，而不是 Framework 依赖。
- GitHub Packages / Maven Central 发布策略。
- 是否区分 internal BOM 与 public BOM。

## 5. 工程治理问题

- 是否补充自动生成 API 文档。
- 是否引入依赖边界检查脚本。
- 是否将 `mvn clean test`、`mvn validate`、边界搜索固化为 CI。
- 历史保留目录是否归档或删除。

## 6. 不应再反复讨论的问题

除非项目阶段变化，以下结论保持冻结：

- Framework 不做业务 Controller、业务 Entity、Mapper 或 migration。
- Framework 不做 starter。
- Framework 不做 demo / example / sample application。
- WebMVC / WebFlux 保持拆分。
- OAuth2 Resource Server 与通用 Web 模块保持拆分。
- trusted-header 身份恢复不再进入 Framework。
- 身份认证只信任经过验证的 Bearer Token。
- `synapse-time` 独立于 `synapse-core`。
- Framework 不做平台文件中心、消息中心、配置中心、审计中心、任务中心。
- Framework 不做 IAM。
- Framework 不做 ABAC / DataScope 业务实现。
- Framework 不做多租户平台实现。
