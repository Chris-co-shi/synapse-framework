# 25-开发前技术决策记录

## 1. 不 Fork 开源框架

决策：不 Fork 现有后台管理框架作为本仓库基础。

原因：

- 历史包袱重。
- 模块边界不一定符合当前目标。
- 技术栈和版本演进不可控。
- 许可证、代码来源和维护风险更高。
- 容易把业务系统结构误带入 framework。

Synapse Framework 只吸收设计经验，不复制业务框架结构。

## 2. 不做启动应用

决策：framework 仓库不提供生产启动类。

允许：

- 测试中的 `TestApplication`。
- `ApplicationContextRunner` 测试。
- 自动配置测试上下文。

禁止：

- 生产 `*Application`。
- 示例业务启动应用。
- 后台管理启动应用。

## 3. 不做业务模块

决策：用户、角色、菜单、组织、订单、库存、流程、工单等业务模型不进入本仓库。

framework 只提供技术抽象，例如：

- `AuthenticatedUser` 是认证主体模型，不是用户表模型。
- `PermissionChecker` 是权限检查入口，不是授权系统。
- `OperationActor` 是操作人抽象，不是员工、用户或组织模型。

## 4. 一阶段模块冻结

决策：一阶段只封板 10 个模块：

```text
synapse-bom
synapse-core
synapse-web
synapse-data
synapse-cache
synapse-security
synapse-oauth2
synapse-audit
synapse-file
synapse-message
```

以下模块不进入一阶段：

```text
synapse-task
synapse-tenant
synapse-data-permission
synapse-cloud
starter
gateway / webflux
```

历史目录可以保留，但不得加入一阶段 reactor。

## 5. Web 栈决策

决策：`synapse-web` 一阶段只支持 Servlet MVC。

原因：

- 大多数业务服务是 MVC / Servlet 栈。
- Gateway 基于 WebFlux，应单独模块处理。
- MVC 与 WebFlux 混在一个模块会导致依赖和自动配置边界混乱。

后续如果需要 Gateway 支撑，优先新增 `synapse-gateway`，而不是把 WebFlux 放回 `synapse-web`。

## 6. Security 决策

决策：`synapse-security` 一阶段不引入 Spring Security Web / SecurityFilterChain / MethodSecurity。

一阶段只做：

- trusted-header。
- `AuthenticatedUser`。
- `SecurityContext`。
- `PermissionChecker`。
- `@RequirePermission` AOP 适配。
- OperationContext 适配。

OAuth2 / JWT / JWK 技术能力放入 `synapse-oauth2`。

## 7. 错误码决策

决策：core 只保留通用错误码，security 细分错误码留在 security 模块。

例如：

- `COMMON_UNAUTHORIZED` 属于 core。
- `COMMON_FORBIDDEN` 属于 core。
- `SECURITY_INVALID_SIGNATURE` 属于 security。
- `SECURITY_PERMISSION_DENIED` 属于 security。

web 只依赖 core，通过 `ErrorCode` 契约处理不同模块错误码。

## 8. Message 决策

决策：`synapse-message` 一阶段只做消息契约，不做运行时消息中心。

保留：

- 消息头。
- Broker / Channel 描述。
- 发送 SPI。
- OperationContext 传播。
- 交互追踪事件。

不做：

- RocketMQ / Kafka / RabbitMQ adapter。
- DB Repository。
- Outbox 默认实现。
- 钉钉 / 企业微信 / 短信 / 邮件 SDK。
- 消息中心后台。

## 9. Cache 决策

决策：`synapse-cache` 一阶段做基础设施能力，不写业务缓存规则。

缓存 key、锁粒度、幂等 key、限流维度全部由消费方决定。

## 10. File 决策

决策：`synapse-file` 一阶段只做文件存储基础抽象和本地轻量实现。

不做文件中心，不做上传下载 API，不做附件表，不做文件权限。

## 11. 注释策略

决策：公共契约和复杂边界必须注释，简单代码不做机械注释。

注释重点解释：

- 为什么这样设计。
- 适用边界是什么。
- 风险是什么。
- 哪些事情不能在这里做。

## 12. 测试策略

决策：一阶段每个模块至少保证核心契约和自动配置可测试。

测试必须避免业务语义污染。除 security 模块必要的 role / permission 外，其余测试样例优先使用 sample、subject、resource、operation、item 等通用词。
