# 数据库迁移规范

## 1. Schema 所有权

谁拥有数据，谁维护 Schema。每个可启动 Platform 服务或业务应用只维护自己拥有的数据表、索引、约束、
视图和初始化数据，不跨服务修改其他服务的 Schema。

Synapse Framework 不拥有业务数据库，因此：

- 不绑定 Flyway 或 Liquibase。
- Framework JAR 不携带自动业务建表脚本。
- 不创建 `synapse-migration`、`synapse-flyway` 或事务模块。
- Outbox、Inbox、审计和幂等表由采用这些能力的可启动服务维护。

## 2. Flyway 使用方式

- 每个可启动服务维护自己的 Flyway Migration 目录和版本序列。
- Migration 与拥有该 Schema 的服务代码一起评审、测试和发布。
- 已发布到任何共享环境的版本化 Migration 不可修改；修复必须新增后续 Migration。
- Repeatable Migration 只用于可安全重复生成的对象，不用于隐藏历史结构变更。
- Migration 失败必须阻止服务启动，不得跳过失败后继续对外提供服务。

## 3. 多数据源

- 每个 Migration 执行器必须显式绑定目标 DataSource、脚本位置和 Schema。
- 禁止依赖“当前路由数据源”或线程上下文猜测 Migration 目标。
- 多数据源版本历史表应独立配置，避免不同 Schema 共享不可解释的版本状态。
- 数据源凭据和目标环境必须在部署配置中明确，不写入 Migration 脚本。

## 4. 变更设计

- 优先采用向前兼容的 expand/contract：先新增兼容结构，再迁移数据，最后在后续版本删除旧结构。
- 大表变更需评估锁表、日志增长、复制延迟、回滚和执行时间。
- 数据回填应可重入、可观察；大规模回填优先由受控任务完成，不阻塞启动 Migration。
- 删除列、收紧约束和类型缩窄属于破坏性变更，必须确认旧版本实例已退出。

## 5. 测试与发布

- 在与生产数据库主版本一致的真实数据库或容器中验证 Migration。
- 测试从当前生产基线升级到目标版本，而不只测试空库初始化。
- 发布前备份和恢复策略必须可执行；回滚通常通过前向修复完成，不修改已发布脚本。
- Release 流水线不得使用 `-DskipTests` 绕过 Migration 相关测试。

## 6. 评审清单

- 当前服务是否拥有被修改的数据？
- 版本号是否唯一，已发布文件是否保持不变？
- 多数据源目标是否显式？
- 失败是否会阻止服务启动？
- 变更是否兼容滚动发布和旧版本实例？
- 是否误把业务建表脚本放入 Framework JAR？
