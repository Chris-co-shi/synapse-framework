# 22-基座与业务域边界设计

## 1. 总原则

Synapse Framework 负责技术基座，业务系统负责业务语义。

判断一段代码能否进入 framework 的核心标准是：

```text
它是否可以被多个业务系统复用，并且不依赖具体业务概念。
```

如果答案是否定的，就不应该进入本仓库。

## 2. 基座可以拥有的内容

Synapse Framework 可以拥有：

- 通用错误码和异常契约。
- 统一响应模型。
- Trace / RequestId / OperationContext。
- 技术操作者模型 `OperationActor`。
- 技术来源模型 `OperationSource`。
- 安全上下文基础抽象。
- trusted-header 解析与校验。
- 权限检查 SPI / Adapter。
- 数据自动填充基础设施。
- 缓存、锁、限流、幂等基础设施。
- 审计事件契约。
- 消息传播和消息交互契约。
- 文件存储抽象。
- 自动配置。
- SPI / Port。
- 轻量技术 Adapter。
- 测试约束。

## 3. 业务域必须拥有的内容

业务系统或后续平台服务必须拥有：

- 用户表。
- 角色表。
- 菜单表。
- 组织表。
- 权限授权后台。
- 订单、库存、工单、流程等业务模型。
- 业务 API。
- 业务 Controller。
- 业务 Entity / Mapper。
- 业务数据库 migration。
- 业务权限码。
- 业务缓存 key。
- 业务文件附件表。
- 业务消息模板。
- 启动应用。
- 前端页面。

framework 不应该为了方便演示而引入这些内容。

## 4. 平台服务与 framework 的边界

部分能力属于平台服务，不属于 framework 一阶段模块。

例如：

- IAM / 用户中心。
- RBAC / ABAC 管理后台。
- Gateway。
- 文件中心。
- 消息中心。
- 任务调度中心。
- 集成中心。
- 主数据中心。
- 工作流中心。

framework 可以为这些平台服务提供底层契约和技术支撑，但不直接实现平台业务。

## 5. 典型边界判断

### 5.1 权限

可以进入 framework：

- `PermissionChecker`。
- `@RequirePermission`。
- `AuthenticatedUser.permissions`。

不能进入 framework：

- 菜单授权页面。
- 角色授权接口。
- 用户角色关系表。
- 业务权限码初始化。

### 5.2 文件

可以进入 framework：

- `FileStorage`。
- `StoreFileCommand`。
- `StoredFile`。
- `LocalFileStorage`。

不能进入 framework：

- 上传 Controller。
- 下载 Controller。
- 附件表。
- 文件权限。
- 文件预览、转码、OCR、水印。

### 5.3 消息

可以进入 framework：

- 消息头契约。
- Broker / Channel 描述模型。
- 发送 SPI。
- 交互追踪事件。

不能进入 framework：

- 消息模板后台。
- 钉钉 / 企业微信 / 短信 / 邮件 SDK 默认实现。
- MQ 消费业务逻辑。
- 消息落库表。

### 5.4 缓存

可以进入 framework：

- CacheClient。
- CacheKey。
- Lock。
- RateLimiter。
- IdempotencyGuard。

不能进入 framework：

- 用户缓存 key。
- 角色权限缓存 key。
- 订单库存锁 key。
- 租户菜单缓存规则。

## 6. 新增代码前检查清单

任何新增代码前必须回答：

1. 是否出现业务名词？
2. 是否需要业务表？
3. 是否需要业务 Controller？
4. 是否需要启动应用？
5. 是否绑定具体平台服务？
6. 是否可以被多个业务系统复用？
7. 是否导致模块反向依赖？
8. 是否可以通过 SPI / Port 交给消费方实现？

只要依赖具体业务语义，就不得进入 framework。
